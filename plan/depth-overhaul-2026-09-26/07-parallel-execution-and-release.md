# Parallel implementation program: contracts, sequencing, gates and measurable completion

This document is an implementation **plan**, not a dispatch, remote write, publication, LMS change or automation. The user asked for enough detail that parallel agents can execute later without collapsing into a generic template. Keep the existing 17-agent roster and the `references/agent-contracts.md` JSON schema, but change the **old `max 90 words body` contract example, ≤90-word A3 copy budgets, and identical nine-screen spine before production**. Their limits contradict the deep-explanation outcome. The schema and phase gates remain; the instructional unit becomes a coherent explanation, not a short card. `scroll-canvas-v1` or `paged-v1` is chosen per topic; 8–14 bands or a stock screen count must not dictate instructional coverage. ## B. Pilot: prove the new depth standard before scaling

Use **three deliberately different** pilot modules, not three cloned paged lessons. Authoring can proceed on separate tracks, but learner-facing release still honors FND-103 → TEC-101 and SRV-101 → SRV-102 prerequisites:

1. **FND-103** (platform concept and live demo): source/identity-to-answer explanation, a real multi-surface capture sequence, an integrated 12-minute partner demo and mistaken-data recovery. It blocks multiple paths.
2. **TEC-101** (technical architecture): detailed ingestion/query/ACL causal diagrams, failure analysis, separate indexed/live paths, security evidence and reviewer proof. It blocks architect and builder paths.
3. **SRV-102** (delivery methodology): lifecycle/RACI, real project gates, decision-making under conflict, a delivery plan and customer status packet; audit the external Ready-for-LMS asset before rewriting.

Also do a targeted **BLD-104/ACC-104 lab-capstone prototype** once the agent claim baseline is locked. The pilot panel includes one seller, one architect, one delivery lead, one accessibility reviewer and a customer-facing SME. Observe actual time-on-task and teach-back; capture misunderstanding on a pretest and unseen posttest, item difficulty, diagram comprehension, missing screenshots and product mismatches. If the pilot cannot demonstrate transfer and defensible customer use, fix the shared standard before 80 more modules. No release merely because lint passes.

## D. Atomic agent contracts: what can run concurrently

After source/claim baseline and blueprint approval, split **one module into independent ≤45-minute work packages**. Example `TEC-101` contracts (copy this pattern, substitute actual IDs/paths/claim IDs only after intake):

1. Researcher, `TEC-101-R1`: extract current indexing/connector passages into `research/ingestion.md`, with URL, date, owner, exact phrase, variant and unresolved questions. Independent `R2` extracts query/ACL/security docs; `R3` retrieves old deck for *conflict comparison only*. Fact Integrity signs one canonical `research/claims.json` before production.
2. Learning Architect, `TEC-101-L1`: map `OBJ-01` source→index and `OBJ-02` query→answer to explanation blocks, worked case, guided simulation, transfer case and evidence. Experience Designer `E1` chooses paged or scroll system, varied density and media positions **after** L1; not a decorative archetype quota.
3. Once claim set + blueprint frozen: Content Writer `C1` writes source-to-index mechanism with numbered steps, example and edge cases; `C2` writes query/ACL mechanism; `C3` writes worked fault case; Graphics `G1` builds ingestion diagram and text equivalent, `G2` builds query/denied diagram and text equivalent; Interaction Engineer `I1` builds source/ACL simulation; Assessment Builder `A1` drafts unseen fault case, rubric and item rationales. These **seven contracts may run in parallel** from the same immutable inputs and own separate files.
4. Graphics `G3` obtains/clears/crops genuine admin/search captures and annotation; if no access, it returns `blocked: capture`, not a synthetic substitute. Brand/Accessibility can review stable markup simultaneously; fact/editorial audit occurs after integration. QA and release agents cannot self-approve author output.
5. Integration lead checks that every explanation, diagram arrow, capture callout, feedback line and rubric decision resolves to claims or is explicitly labeled as a scenario assumption. If a fact changes, upstream Researcher/Fact Integrity issues a new baseline and dependent packages rerun; downstream author never patches a fact silently.

**Machine-readable contract template:** `{task_id,module_id,agent,sub_agent,mode,objective,inputs,output,constraints,acceptance,out_of_scope,on_block,retry_policy,returns}` as specified in the studio skill. Inputs are exact versioned paths/IDs and claim-registry digest, not a vague instruction to “research Glean.” Replace `max 90 words body` with `complete mechanism, preconditions, worked example and failure; no word cap; edit only assigned section`. A content task must not alter diagram, rubric or claims; a diagram task must not invent labels/behavior; a QA task must not change release metadata. Retry once on evidence, then `needs_sme` or systemic halt per skill.

**Concurrent capacity:** three modules active by default (five hard maximum), four contracts per module by default; at most one package release. The seven-way pilot example is a *dependency graph*, not permission to launch seven contracts simultaneously under the default cap: issue C1/C2/G1/A1, integrate, then C3/G2/I1/G3 in bounded batches. Research and memory recall can overlap. Content/graphics/interactions/assessment overlap only after fact baseline and blueprint. Fact → brand/a11y → packaging → runtime/LMS QA → release remain serial. Keep a running versioned status table with blocker and next action, but do not write over `plan/status.json` until implementation is authorized.

## E. Required artifact contract, deeper than the current generator

For every module, the repository should contain:

- `module.yaml` with audience, level, estimated **reading/practice/assessment** time and measurable outcomes; `sources.json` with primary passage/owner/freshness; `research/findings.md`, `claims.json`, conflicts and reviewer decisions; `design/blueprint.*` mapping outcomes → sections → practice → evidence and `design/experience.yaml` with deliberate format choice.
- `content/` with explanatory lessons in full, two worked examples where the mechanism has meaningful variants, one failed/negative example, real-world task packet, glossary and job aid. Assert claim IDs on explanations, examples and feedback. No generic hero/reveal/badge filler counted as instruction.
- `assets/` with semantic diagram source, labeled nodes/edges, long text description, real UI captures where taught, redaction/license/approval/date in manifest, caption and 90-day UI review. `interactions/` with keyboard/text equivalent and meaningful consequences, not a decorative drag.
- `assessment/` with diagnostic, guided practice, **unseen transfer case**, role-authentic performance artifact/rubric and optional item bank; separate answers/rater guide stored outside runtime package. Each hard gate has a reproducible negative test. A 2.5-hour workshop cannot pass on five MCQs.
- `qa/` with fact/editorial, diagrams and screenshots, WCAG 2.2 AA, screen reader/zoom, runtime/SCORM, regression, privacy/security, live browser evidence, LMS import/score/restore, SME sign-off and **the current ZIP SHA**. Release metadata records source commit, case packet version, human reviewer and approved badge membership. Protect any sensitive lab data and remove it from shipped packages.

## F. Independent quality gates and thresholds

| Gate | Test evidence; failure condition |
|---|---|
| Content depth | Two SMEs independently answer: can a partner explain **why and how** it works, carry out the task, diagnose failure, defend alternatives? Every target has explanation, worked example, guided practice, transfer case. A check-box-only concept card fails. |
| Factuality/currentness | Every factual sentence/diagram arrow/quiz rationale has a verified claim or documented scenario assumption. Product behavior/security/pricing source within 90 days (or rechecked before release); program policy within 180 days. Contradictory deck claim blocks until owner ruling. |
| Visual comprehension | Diagram answers a stated question and includes states, direction, actors, boundary, failure and text equivalent where applicable. Screenshots are real, redacted, date-stamped, approved, current, and bundled offline. Have a novice interpret diagram unaided; revise if the key decision is missed. |
| Authentic assessment | Unseen case, rubric, observed artifact/lab, safety hard gates, explanatory remediation and alternate retake. Human scorers pilot two submissions to agreement on pass/fail and criteria. Quiz-only pass fails for lab/accreditation. |
| Engineering/accessibility | `lint_module.py`, `validate_scorm.py`, `validate_accreditations.py`, runtime harness, actual keyboard/screen reader/zoom and real-browser responsive check; no broken image, external runtime dependency, leaked authoring key, unsafe storage or fake progress. |
| Provenance/LMS | ZIP hash = sidecar = QA report = release record; all artifacts versioned. Import into actual LMS, first run, fail/pass, resume, score, concurrent module isolation and reattempt. No green report for older bytes; no release/announcement without authorized publication and independent review. |
| Learning outcome | Pilot compares pretest to *unseen* task and observes teach-back, not just quiz pass and time. After launch review abandonment by section, first-attempt success, false-positive pass, real artifact quality and SME-reported field readiness; revise item/copy/visual based on evidence. |
